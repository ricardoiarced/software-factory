# Cross-Client Shared Git Repositories Are Structurally Inadmissible

Factory refuses Runs through any Repository whose Git common directory is bound to Checkouts of more than one Client. A Git common directory holds repository-wide mutable state — refs, objects readable by SHA, reflogs, configuration, hooks, and linked-worktree metadata including every linked worktree's path and index — and Git provides no per-Client access-control boundary inside it, so Project Data Isolation cannot be proven for one Client while another shares that repository identity.

The refusal is structural, not provisional: no evidence pack or additional pre-Run inspection can make a cross-Client shared common directory Run-admissible under the current isolation model. Snapshotting refs or fencing before the Run describes a momentary state, creates no access boundary, and leaves a TOCTOU gap between verification and execution. The Client is the confidentiality boundary, and the escape hatch is architectural: a future design might materialize a Client-specific repository instance inside an isolated execution environment, at which point the Run is against that instance, not against the cross-Client shared Repository — such a mechanism would supersede this ADR rather than amend it.

Registration refuses to create the condition. Explicit `--repository` selection of a Repository already bound to another Client's Checkout refuses, and a Checkout whose observed common directory resolves to a Repository bound to a different Project refuses unless that Repository is explicitly selected: implicit Repository reuse is permitted only for additional Checkouts of the same Project, because the same Client establishes permission eligibility, never sharing intent. The Run gate independently enforces the rule as fail-closed defense against legacy data, store corruption, drift, and future defects: store invariants, selected-Repository cross-client association, fresh proof, and foreign-match classification each refuse, with distinct diagnostics for store-detected (an integrity and policy failure) and drift-detected (an observed Git identity change) sharing — both terminating at the same invariant that no Run is admitted when one Git common directory spans Clients.

Repositories explicitly shared by multiple Projects of the same Client are not covered by this refusal: their repository-wide Git state is authorized shared data for those Projects, not sibling-private data.

Factory is stricter than Git itself — a topology Git permits may still be inadmissible for a Run — and that is the price of a simple fail-closed boundary that never claims isolation the repository structure cannot enforce. Out of scope here: presentation of shared-Repository topology in `factory doctor project` (tracked on the doctor decision), traceability rows and implementation tests (tracked in the sequencing ticket's implementation slices), and any change to the certified sandbox recipe, which this decision requires none of.
