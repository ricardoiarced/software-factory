# A Git common directory shared across Clients never admits a Run

A Repository whose Git common directory is bound to Checkouts of more than one Client is structurally, permanently inadmissible: no Run is ever admitted against it, and the refusal is a policy about the topology, not a missing-evidence state that more inspection could cure. A Git common directory holds repository-wide mutable state — refs, packed-refs, objects readable by SHA even when unreferenced, reflogs, config, hooks, and `worktrees/<name>/gitdir` paths plus per-worktree indexes — and Git provides no per-Client access-control boundary inside it, so Project Data Isolation is unprovable for one Client while another shares that repository identity. The Client is the confidentiality boundary: same-Client cross-Project Repository sharing stays admissible, because Repository state explicitly bound to several Projects of one Client is authorized shared data for those Projects, not sibling-private data.

The policy is enforced twice, by construction and by verification. Registration prevents creating the state: implicit Repository reuse is permitted only for additional Checkouts of the same Project, sharing with a sibling Project requires the explicit `--repository REPO` form, and cross-Client explicit selection refuses outright. The Shared Run Gate then re-establishes the rule every Run, fail closed: it re-reads the identity store and refuses a corrupt identity graph, rescans every Checkout referencing the selected Repository through its Projects to their Clients, and compares the fresh Git proof against the pinned Checkout and Repository identities, so corrupted, migrated, manually edited, or otherwise unexpected state cannot bypass what registration prevents. The store-detected and drift-detected sharing conditions keep distinct frozen diagnostics — an integrity/policy failure versus an observed Git identity change — while both terminate at the same invariant, and dirtiness of the observed working tree never gates: it warns.

A runtime evidence pack over the same shared common directory was rejected — ref snapshotting, foreign-ref checks, or pre-Run fencing describe a momentary state, establish no access boundary, and leave a TOCTOU gap between verification and execution. The only future path is architectural: a genuinely isolated repository instance, for example a Client-specific clone or snapshot materialized inside an isolated execution environment. Such a mechanism would supersede, not amend, this decision — at that point the Run is against that instance, not against the cross-Client shared Repository.
