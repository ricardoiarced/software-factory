# Fail closed with durable Run Records and launch atomicity

Every Run opens one crash-durable audit record after successful CLI parsing and before any operational selection, scope resolution, composition, or admission work; exit-2 usage errors, help, version, and the `factory project` administration namespace precede the Run boundary and create no record. The record is a separate per-Run JSON file under a private `runs` directory of the configuration directory, named for a cryptographically random, immutable `run_` ID, so one Run's audit trail is written and updated independently of every other Run, with no cross-Run lock and no append tail that a crash could leave ambiguous. Opening the record and writing the Launch Commit fail closed: a store that cannot be opened refuses the Run before selection, and a Launch Commit that cannot be made durable refuses before process creation, which makes "process creation without a preceding crash-durable Launch Commit" unrepresentable rather than prohibited. The commit records the admitted launch plan — Harness, canonical executable, exact invocation, certified environment edits — immediately after today's final pre-spawn check and before `Popen`, so the durable authorization is exactly what is about to execute; later gate slices enrich that authorization and insert the Launch Boundary Recheck before the same commit point.

The record holds only facts the pre-gate Run path actually knows. Unset evidence stays absent — never a synthesized `null` — so audit readback can distinguish "not known" from "known empty"; Factory-composed request text (Context Source payloads, standard input) never enters the record, while the command line does through the pinned `factory-argv-v1` serialization: the instruction is the person's own argv, and an ASCII-escaped canonical JSON form records every host byte losslessly. Classified pre-launch failures commit a structured refusal (stage, diagnostic, admission facts) through hooks that later gate slices extend; refusal recording is best-effort so a broken store can never mask the diagnostic the person actually needs, and the same best-effort rule covers post-launch outcomes (exit status, signal, spawn failure), whose absence honestly reads as "outcome unknown" after a Factory crash.

A single append-only audit log was rejected: it couples every Run's durability to one file and one lock, and a crash mid-append leaves a tail that cannot be distinguished from tampering. Strong refusal recording — refusing the Run because its refusal could not be recorded — was rejected: the Run has already refused, and turning a broken audit store into a different, louder failure only buries the cause. Synthesizing absent evidence as explicit nulls was rejected for the reason above, and storing request text or Context payloads was rejected because bulk and secret-bearing content has no audit value the argv and file labels do not already provide.
