# Strict configuration checks in Codex and Claude Code

_Research date: 2026-09-28. Local CLI evidence: Codex 0.158.0 and Claude Code 2.1.283 on Linux x86_64. This is an input to the wayfinder policy decision, not a change to Factory's launch contract._

## Findings

| Harness | Current strict flag | What it checks | Factory today |
| --- | --- | --- | --- |
| Codex | `--strict-config` | Unknown configuration fields in the loaded `config.toml` and, in the installed 0.158.0 CLI, unknown `-c` overrides cause a configuration error before a Run. [OpenAI CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli) and local probe below. | Already passes `--strict-config` with `codex exec`, `--ignore-user-config`, and Factory-generated `-c` overrides. It also inspects feature and MCP output before launch. [`_codex.py`](../../_codex.py) |
| Claude Code | `--strict-mcp-config` | Restricts MCP servers to those supplied by `--mcp-config`; it is not a strict settings validator. [Anthropic CLI reference](https://code.claude.com/docs/en/cli-reference) | Already passes `--strict-mcp-config` with `--restricted`, `--safe-mode`, and inline `--settings`. [`_claude.py`](../../_claude.py) |

OpenAI documents `--strict-config` for runtime commands including `codex exec` as an error on configuration fields the running version does not recognize. The same CLI documents `--ignore-user-config` as skipping `$CODEX_HOME/config.toml` while retaining authentication. Consequently, Factory's current strict flag validates its effective generated overrides but **does not audit stale fields in the user's ignored config file**. The latter is expected under Factory's current isolation design. [OpenAI CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli); [`_codex.py`](../../_codex.py).

The installed Codex 0.158.0 accepted `--strict-config` on `exec`. With an isolated `CODEX_HOME/config.toml` containing `factory_unknown_probe = true`, `codex exec --strict-config --ephemeral --skip-git-repo-check -` exited 1 before inference and named the unknown field. With `--ignore-user-config -c factory_unknown_probe=true`, it likewise exited 1 and identified the unknown `-c/--config` override. These are local version observations, not a claim about every future release. Factory already pins executable version, digest, and host evidence through its Compatibility Set and certification process. [`_codex.py`](../../_codex.py); [Codex certification record](../../certification/results/2026-09-28-linux-x86_64-codex-npm-0.158.0.md).

Anthropic explicitly defines `--strict-mcp-config` as selecting MCP sources. Its `--restricted` mode ignores user, project, and local settings files but still applies managed settings and `--settings`. `--settings` is merged above ordinary settings and below managed settings. Factory's inline sandbox and permission settings therefore remain the relevant settings input; `--strict-mcp-config` does not validate those keys. [Anthropic CLI reference](https://code.claude.com/docs/en/cli-reference); [Anthropic settings precedence](https://code.claude.com/docs/en/settings); [`_claude.py`](../../_claude.py).

Anthropic documents that invalid JSON or schema-rejected values in ordinary settings can be skipped, and that individual invalid entries can be dropped while the rest remain active. A noninteractive `-p` run shows no repair dialog and can continue after skipping broken settings; `claude doctor` lists rejected entries. The published JSON schema helps editors, but Anthropic warns it may lag the latest CLI, so schema validation alone cannot prove runtime acceptance. [Anthropic settings errors and precedence](https://code.claude.com/docs/en/settings).

There is no documented Claude Code flag analogous to Codex `--strict-config` for rejecting every unknown settings key at startup. In an isolated local `CLAUDE_CONFIG_DIR`, `claude doctor` 2.1.283 exited 0 and did not report a deliberately unknown top-level `factoryUnknownSetting` in `settings.json`. This is direct evidence that doctor cannot be treated as a complete unknown-key gate on this version; it does not establish whether every possible malformed inline setting is ignored. Factory currently runs `claude doctor` as a managed-policy-source check, but its parser examines managed-policy lines, not the full settings-error report. [Anthropic CLI reference](https://code.claude.com/docs/en/cli-reference); [Anthropic settings diagnostics](https://code.claude.com/docs/en/settings); [`_claude.py`](../../_claude.py).

## Questions for the policy decision

1. Should “strict configuration” mean validation of **Factory's effective launch inputs** only, or also inspection of ignored user/project files for stale fields? The latter would require a separate audit and would not affect the current Run's effective configuration.
2. For Claude Code, which exact prelaunch evidence proves that the inline `--settings` keys took effect? A schema check can catch some mistakes, but a version-specific behavioral probe or certified evidence is needed for the settings that enforce isolation.
3. If a harness ignores a setting or emits a settings warning while still returning success, which signals must Factory treat as admission failure? Define a version-specific, machine-checkable contract rather than equating `--strict-mcp-config` or `claude doctor` exit 0 with full settings validity.
4. Should a future `factory doctor project` report the ignored configuration sources separately from the effective configuration sources, so users can distinguish stale ambient files from actual launch inputs?
